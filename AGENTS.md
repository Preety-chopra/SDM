> Project-level instructions for AI coding agents working on this Laravel application.

## 1. Source of Truth

At the beginning of any Laravel installation or initial setup session:

1. Fetch and read:
   - https://laravel.com/for/agents
2. Treat the returned Markdown as the source of truth for Laravel installation and setup.

4. Explicit project decisions in this file override Laravel defaults only where the Laravel agent instructions allow the developer's stated preferences to take precedence.
5. After Laravel Boost is installed, immediately read the agent guideline files generated by Boost, such as `AGENTS.md` or `CLAUDE.md`, and follow them together with this file.

Do not silently change the agreed technology stack.

## 6. Laravel Sail Setup

Laravel Sail is mandatory for local application development.

If Sail is not installed:

```bash
composer require laravel/sail --dev
```

Install Sail:

```bash
php artisan sail:install
```

Select MySQL as the required database service.

Do not add Redis, Meilisearch, Selenium, Mailpit, or other services unless the application needs them or they are explicitly requested.

After Sail installation, inspect `compose.yaml`.

Confirm:

- the application service uses PHP 8.5 unless intentionally changed;
- the MySQL image is `mysql:8.4`;
- the application service depends on the MySQL service where appropriate;
- the database host is the Docker service name `mysql`.

Start containers:

```bash
./vendor/bin/sail up -d
```

On Windows, run Sail from WSL2 when required by the Laravel Sail environment.

Once Sail is working, prefer Sail commands instead of host commands.

Examples:

```bash

./vendor/bin/sail composer --version
./vendor/bin/sail artisan --version
./vendor/bin/sail node --version
./vendor/bin/sail npm --version
```

For the remainder of this document, `sail` means:

```bash
./vendor/bin/sail
```

Do not assume a global `sail` shell alias exists.

## 10. Application Architecture

The application must follow a Service Repository architecture.

Use the following responsibility flow:

```text
Route
  -> Controller
      -> Service
          -> Repository Interface
              -> Eloquent Repository
                  -> Model / Database
```

Validation, authorization, presentation, and domain behavior should remain separated.

Recommended project structure:

```text
app/
├── Contracts/
│   └── Repositories/
│       └── ExampleRepositoryInterface.php
├── Http/
│   ├── Controllers/
│   ├── Requests/
│   └── Resources/
├── Models/
├── Providers/
├── Repositories/
│   └── Eloquent/
│       └── ExampleRepository.php
├── Services/
│   └── ExampleService.php
└── ...
```

Alternative names already established in the repository should be preserved rather than creating duplicate conventions.

### Controllers

Controllers must be thin.

Controllers may:

- receive requests;
- invoke Form Requests;
- invoke authorization;
- call application services;
- return redirects, views, or resources.

Controllers should not contain:

- complex business rules;
- large Eloquent queries;
- transaction orchestration;
- reusable domain calculations.

### Services

Services contain application and business orchestration.

Services may:

- coordinate multiple repositories;
- apply business rules;
- manage application-level workflows;
- start database transactions where a workflow must be atomic;
- dispatch domain/application events;
- call external integrations through abstractions.

A service should not become a generic dumping ground.

Prefer cohesive services centered around a use case or domain capability.

### Repositories

Repositories are responsible for persistence and retrieval behavior.

Repositories may:

- query Eloquent models;
- create, update, and delete persisted records;
- implement reusable data access queries;
- encapsulate persistence details.

Repositories should not:

- contain HTTP request logic;
- return redirects or views;
- perform authorization;
- contain unrelated business workflows.

### Repository Interfaces

Define repository interfaces when a repository is consumed by services.

Example:

```php
<?php

namespace App\Contracts\Repositories;

use App\Models\Employee;

interface EmployeeRepositoryInterface
{
    public function findById(int $id): ?Employee;
}
```

Implementation:

```php
<?php

namespace App\Repositories\Eloquent;

use App\Contracts\Repositories\EmployeeRepositoryInterface;
use App\Models\Employee;

final class EmployeeRepository implements EmployeeRepositoryInterface
{
    public function findById(int $id): ?Employee
    {
        return Employee::query()->find($id);
    }
}
```

Bind interfaces to implementations using Laravel's service container.

Use either `AppServiceProvider` or a dedicated provider such as `RepositoryServiceProvider`.

Example:

```php
use App\Contracts\Repositories\EmployeeRepositoryInterface;
use App\Repositories\Eloquent\EmployeeRepository;

$this->app->bind(
    EmployeeRepositoryInterface::class,
    EmployeeRepository::class,
);
```

If a dedicated service provider is created, register it using the conventions of the installed Laravel 13 application.

Prefer constructor dependency injection.

Do not instantiate repositories manually with `new` inside controllers or services.

## 11. Supporting Laravel Patterns

Use Laravel conventions around the Service Repository architecture.

### Validation

Use Form Request classes for non-trivial request validation.

Example:

```bash
sail artisan make:request StoreEmployeeRequest
```

Do not duplicate validation rules across controllers when they can be centralized.

### Authorization

Use policies, gates, or middleware.

Do not rely on hidden buttons or frontend checks as authorization.

### Database Transactions

Use transactions in services when multiple writes must succeed or fail together.

Example:

```php
return DB::transaction(function () {
    // Coordinated repository calls...
});
```

### Eloquent

- Define relationships on models.
- Avoid N+1 queries.
- Use eager loading intentionally.
- Use scopes for reusable model-level query constraints where appropriate.
- Avoid uncontrolled mass assignment.
- Add casts for dates, booleans, enums, JSON, and other domain values as appropriate.

### API Responses

If APIs are added, prefer Laravel API Resources.

### Events / Jobs

Use queued jobs for slow or asynchronous work.

Keep jobs small and retry-safe.

## 12. Test-Driven Development

All feature development follows TDD.

Use the Red -> Green -> Refactor cycle.

### RED

Before implementing a behavior:

1. Write or update a test describing the expected behavior.
2. Run the smallest relevant test command.
3. Confirm the test fails for the expected reason.

Do not write production code before the failing test unless the task is purely configuration, scaffolding, or a non-behavioral change where a meaningful test is not applicable.

### GREEN

Implement the minimum production code required for the test to pass.

Run the targeted test again.

### REFACTOR

After the targeted test passes:

- remove duplication;
- improve names;
- move code into the correct architectural layer;
- preserve behavior;
- rerun the relevant tests.

### Final Verification

Before declaring a task complete:

1. run the targeted tests;
2. run the broader related test group;
3. run the complete test suite when practical;
4. run frontend build checks if frontend files changed;
5. run code formatting.

## 13. Testing Strategy

Pest is the preferred test framework for a new project unless the project is already standardized on PHPUnit.

Laravel supports both Pest and PHPUnit.

### Test directories

Use:

```text
tests/
├── Feature/
└── Unit/
```

### Feature Tests

Prefer feature tests for:

- HTTP requests;
- authentication;
- authorization;
- validation;
- controller/service integration;
- database workflows;
- repository behavior that uses the database;
- complete use cases.

Most application behavior should be covered by feature tests.

### Unit Tests

Use unit tests for:

- isolated domain calculations;
- pure service logic;
- value objects;
- small components that do not need Laravel bootstrapping or the database.

Do not mock everything merely to call a test a unit test.

### Database Tests

Use Laravel database testing helpers such as `RefreshDatabase` where appropriate.

Tests must use the testing database.

Laravel Sail's MySQL setup normally provides a dedicated `testing` database.

Do not allow automated tests to write to the normal local development database.

### Test commands

Run all tests:

```bash
sail artisan test
```

Run a single test file:

```bash
sail artisan test tests/Feature/ExampleTest.php
```

Filter a specific test:

```bash
sail artisan test --filter="test name or method"
```

Stop on first failure while iterating:

```bash
sail artisan test --stop-on-failure
```

Do not mark a task complete with known failing tests caused by the change.

## 14. Testing Service / Repository Code

When testing controllers:

- test externally visible behavior;
- avoid asserting implementation details;
- verify response, validation, authorization, redirects, view data, or JSON.

When testing services:

- test business rules and workflow results;
- use mocks/fakes for truly external boundaries where useful;
- prefer real repositories for high-value integration tests where database behavior matters.

When testing repositories:

- use a test database;
- verify actual Eloquent/query behavior;
- cover important filters, relationships, ordering, pagination, locking, and constraints.

Do not mock Eloquent solely to avoid using Laravel's database test tools.

## 17. Security Rules

Never:

- commit `.env`;
- commit credentials, tokens, passwords, or private keys;
- expose server secrets through `VITE_*` variables;
- trust client-side authorization;
- concatenate untrusted data into raw SQL;
- disable CSRF protection without a documented requirement;
- weaken validation merely to make a test pass.

Always:

- validate request input;
- authorize protected actions;
- escape Blade output by default;
- use parameter binding / Eloquent / Query Builder;
- review uploaded file validation;
- review mass-assignment rules;
- protect sensitive routes.

## 18. Database Change Rules

For every schema change:

1. create a migration;
2. write or update tests;
3. consider existing production data;
4. add foreign keys where appropriate;
5. add indexes for common filtering/joining requirements;
6. verify rollback behavior;
7. run migrations in the Sail environment;
8. run tests.

Example:

```bash
sail artisan make:migration create_examples_table
sail artisan migrate
sail artisan test
```

Never edit an old migration that may already have been executed in shared environments unless the project explicitly allows it.

## 20. Audit Logging

Auditable application activity must produce durable audit logs for accountability and investigation.

At minimum, audit:

- authentication events and relevant access failures;
- creation, update, and deletion of important business records;
- workflow and status transitions;
- role, permission, account-status, and other security-sensitive changes;
- privileged administrator actions.

Audit entries should capture, where applicable:

- the actor's user ID;
- the action or event name;
- the affected entity type and ID;
- relevant before and after values;
- the timestamp;
- request context such as IP address, user agent, or request/correlation ID when useful.

Create audit records in the service layer and within the same database transaction as the audited change when atomicity is required. Audit logs must be append-only for normal application users, access-controlled, and covered by tests.

Never record passwords, password hashes, authentication tokens, API keys, session identifiers, private keys, or other secrets. Avoid storing complete request payloads or unnecessary personal data; record only the fields required for the audit purpose.

Prefer an audit mechanism already established in the repository. Do not introduce a new audit package without approval when the existing application can meet the requirement cleanly.

## 22. Agent Working Style

When implementing a task:

1. Inspect the existing code before creating new abstractions.
2. Identify the relevant route, controller, service, repository, model, migration, and tests.
3. State important assumptions only when necessary.
4. Make the smallest coherent change.
5. Write the failing test first.
6. Implement through the required architecture.
7. Run targeted tests.
8. Run formatting.
9. Run broader tests.
10. Summarize:
    - what changed;
    - files changed;
    - tests executed;
    - any remaining risks or decisions.

Do not:

- rewrite unrelated code;
- change the technology stack without approval;
- skip tests to save time;
- place business logic in Blade templates;
- place database queries directly in Blade;
- place complex business logic in controllers;
- bypass repositories from services when a repository exists for that domain;
- invent Laravel APIs without checking current Laravel 13 documentation.
